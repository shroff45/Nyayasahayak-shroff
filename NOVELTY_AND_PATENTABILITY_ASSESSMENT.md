## 2. What the repository actually is

Verified facts, not impressions:

- **Frontend-only SPA.** React 18 + Vite + Tailwind + three.js/GSAP animations. No `package.json` dependency implies a server, database or auth provider. `grep` for `axios|fetch(|express|prisma|firebase` returns **zero** application network calls other than direct browser→Gemini SDK calls. - **Hygiene:** single squashed commit, no CI (`.github/` absent), no tests of any kind, 88 explicit `any`, 805 hits for `mock|simulat|placeholder|todo|hardcod|demonstration`, 20+ scratch log files (`build_log_*.txt`, `tsc_full_output_*.txt`, `errors.log`) and a stale `dist/` bundle committed to git. ### 3.1 Empirical verification — I ran the code, not just read it

`tools/ledger_repro.cjs` (added with this review) re-implements the ledger's logic verbatim and asserts each README claim. Run `node tools/ledger_repro.cjs`. **1 of 12 claims holds.** Results worth stating precisely, because two of them correct a naive reading of the source:

**What actually works (credit where due).** The chained-hash integrity mechanism is correctly built: `verifyChainIntegrity()` recomputes each block's digest from the live `block.data` and compares it to the stored `hash`, so an attacker who mutates `block.data` in place **is** detected — `isValid` flips to `false` and the index appears in `corruptedBlocks`. For a teaching demo of "why blockchains are tamper-evident," that part is textbook.

**Four failure modes that matter:**

1. **Nothing persists.** `src/services/akhandLedger.ts` contains no `localStorage`, no IndexedDB, no `fetch`, no driver — just `let blockchain: BlockchainBlock[] = []`. Verified by test B1. Consequence in the real flow: citizen uploads via `VoiceFilingInterface` → `addBlock()` → anchor "succeeds" → a page refresh re-seeds to genesis → the judge's `HashVerifier` scans an empty array and returns **`NO_MATCH` for a perfectly intact exhibit**. The product's central promise ("evidence remains verifiable") inverts into a false tamper accusation on reload.
2. **No authority binding → tampering is laundered, not detected.** `addBlock()` accepts any object from any caller: no signature, no key, no role check, no HMAC (verified by test B2 — the file matches no `sign|signature|publicKey|certificate|hmac` pattern). A doctored video hashed and uploaded through the *same* Evidence Locker UI produces a legitimate ledger entry that the judge's verifier happily matches. This is the exact hole that Microsoft's US 11,139,954 closes with a context schema + participant authorization ("*in response to a determination that the participant is not authorized … raise an alert*") and that OriginStamp's docs warn about explicitly ("*anchoring proves a hash existed; it does not prove who submitted it — you must sign the hash*").
3. **A write-capable attacker erases the evidence.** Verified by test A3: mutate `block.data`, recompute `block.hash = calculateHash(block)`, and `verifyChainIntegrity()` reports **valid** again while the exhibit digest is swapped. Without an external validator (real chain, TSA, or FSL co-signature), "tamper-evident" only holds against readers who cannot write — which is not the threat model for police-held evidence.
4. **Split-brain ledgers.** Three copies of the module exist. Two emit incompatible digest formats (`PQC-v1:KYBER-1024:<hex>` vs `PQC-v1:KYBER-1024-SALT-<hex>`, test E1) and, being separate ES modules, hold separate arrays. Evidence anchored through `features/nationals` (SmartBail panel, that tree's voice-filing path) is **structurally invisible** to `src/components/QuantumHashProof.tsx` and `src/personas/judge/pages/HashVerifier.tsx`, which read `src/services`. Meanwhile `src/core/services/trust/akhandLedger.ts` (302 lines, carrying the "Post-Quantum Cryptography" header that a reviewer reads first) has **zero importers** — dead code (test E2).

And the two cryptographic claims, measured rather than asserted:

- **ML-KEM/Kyber is absent, provably by size.** `ML-KEM-768` encapsulation keys are 1,184 bytes and ciphertexts 1,088 bytes. The "PQC" digest this code emits is **32 bytes** (64 hex chars) — test C1. There is no KEM material, hence no keypair, no encapsulation, no decapsulation, no sharing of a secret: the protocol's entire purpose.
- **The "salt" adds exactly zero bits.** `calculateHash = SHA256(SHA256(data) ‖ "KYBER-1024-ENCAPSULATED-SALT")`. The constant is in the source, visible to every adversary, so it is neither a key nor a secret (test C2). Worse, hashing the *hex string of* an inner digest and truncating to the outer 256 bits cannot increase security; against Grover, SHA-256 offers ~128-bit preimage resistance, and the accepted remedies are a wider digest (SHA-384/512) or a hash-based signature (SPHINCS+/LMS) — neither present.
- **`merkleRoot` is not a Merkle root.** For the same four leaves, `SHA256(JSON.stringify(leaves))` ≠ the pairwise tree root (test D). So no inclusion proof — the one feature that makes anchored timestamping cheap *and* independently verifiable — can ever be produced from this structure.

**Pattern across all 13 rows:** each claimed "novel technology" is either (a) a standard, decade-old, heavily-published practice; (b) a statutory requirement being restated in code; (c) an `if` statement; or (d) in the case of the quantum fingerprint, non-functional. The recurring vocabulary in the source is "simulate", "mock", "Optional implementation", "would go here", "as requested".

## 5. Patentability — India

### 5.1 The statutory gates

An Indian patent needs: manner of new manufacture (s.2(1)(j)), novelty (s.2(1)(l), absolute/worldwide), inventive step (s.2(1)(ja)), industrial applicability (s.2(1)(ac)) — **and** it must clear every carve-out in s.3.

**s.3(k): "a mathematical or business method or a computer programme *per se* or algorithms."** Only the computer-programme limb carries "per se" (confirmed by the IPO's own guidelines and *Ferid Allani v. UOI*, Delhi HC, W.P.(C) 7/2014, 12 Dec 2019). The saving doctrine is **technical effect / technical contribution**:

- *Ferid Allani* (2019): the bar is on programmes *per se*; show a technical effect.
- *Microsoft Technology Licensing v. Asst. Controller* (2023:DHC:3342) and the Madras HC's 3 July 2024 *Microsoft* judgment: a general-purpose-computer implementation is fine **if** it "results in a technical effect that improves the system's functioning and efficacy … and is not limited in its impact to a particular application or data set".
- *Raytheon v. Controller General* (2023:DHC:6673): **novel hardware is not required** — that requirement "lacks any basis in law".
- *OpenTV v. Controller* (2023:DHC:3305): the **business-method** exclusion is an **absolute bar** — no technical-effect rescue, unlike the EPO/UK.

**CRI Guidelines 2025** (notified 29 July 2025, superseding 2017) are now the operative examination framework and they cut *against* this project specifically:

- **Blockchain:** "claims directed to the theoretical concept of a distributed ledger are excluded. A practical implementation that integrates blockchain with physical systems and delivers a concrete technical outcome may not be." The specification must fully disclose **the consensus mechanism and its parameters, smart-contract logic, block data structures and linkages, and any IoT/oracle integration**. → `akhandLedger.ts` discloses no consensus (there is one writer, in one browser tab), no network layer, no real smart contract, and `merkleRoot` is either a single-payload hash or `""`.
- **Quantum/PQC:** abstract invocations without concrete implementation are excluded; you must enable a skilled person to reproduce the mechanism. → A concatenated salt string is not a mechanism.
- **AI/ML:** heightened sufficiency — you must disclose architecture, dataset characteristics, pre-processing, training parameters, and **validation metrics** proving the claimed effect. → `vidhikRAG` has no model, no corpus, no eval. `geminiService` is a prompt with a JSON schema (which is standard SDK usage).
- **Form over substance:** "the focus should be on the underlying substance of the invention, not the particular form in which it is claimed." → Drafting today's code as "a method and system comprising …" will not help.
- **AI-generated vs AI-assisted:** the Guidelines state AI-*generated* inventions (autonomous creation, minimal human input) are **not patentable**, since §6 requires a "person"; AI-*assisted* inventions remain assessable on ordinary criteria.

### 5.3 Novelty: the single-reference problem

Indian anticipation requires one prior document disclosing all essential features (combination belongs to inventive step). Two references do that for this project's core:

## 7. Disclosure status & the one urgent item

**This is the finding that actually needs your attention.**

- Novelty in India is judged on an **absolute, worldwide, pre-priority-date publication** basis (s.2(1)(l)); "publication in any document" includes online availability, in any language, anywhere.
- **India has no general grace period for an inventor's own disclosure.** The only relief is s.31 — display at a **Central-Government-notified** exhibition, or a paper read before / published in the transactions of a **learned society** — within 12 months, and since **15 March 2024** claimed procedurally via **Rule 29A + Form 31** with fee. s.29 covers publication *derived from you without your consent*. Ordinary blog/GitHub/demo/Devpost/social posts are **not** covered. (Compare: the US *does* give a 1-year grace for the inventor's own disclosure, 35 U.S.C. §102(b)(1).)
- **Good news, verified:** `api.github.com` reports `shroff45/Nyayasahayak-shroff` as **`"private": true`**, created `2025-12-28T12:03:46Z`, last pushed same day, **0 forks, 0 stars**. On the visible record there has been **no self-disclosure**, so your Indian/absolute-novelty position appears intact — *if the repo was never public and never mirrored*.
- **Bad-news scenarios you must check today:** the README says the project was "Designed for **OpenAI NextWave Hackathon 2024**". If the demo, submission, deck, video, or a public repo existed at any point in 2024–2025, then (i) India novelty may already be gone with no cure; (ii) the US 1-year clock from that disclosure may already have run; (iii) EP/PCT absolute novelty is gone. A hackathon submission judged publicly, posted on Devpost/YouTube/X/LinkedIn, counts as enabling public disclosure in most analyses.
- **If the earliest disclosure really is 28 Dec 2025**, the US grace window closes **~28 Dec 2026 — about 71 days from today.** That is your hard deadline for a US provisional (or an India provisional + PCT) if you want anything at all.
- **Stop the clock now, free:** (1) keep the repo private; (2) do not publish, demo, blog, tweet or submit anywhere; (3) do **not** honour the README's "MIT License" claim as a plan — an MIT release is a permanent, irrevocable, worldwide licence to practise and destroys novelty everywhere on the day it is published; (4) optionally create evidence of conception with a hash anchored *in the past* (git-sign + OpenTimestamps/OriginStamp on the source tree + a dated inventorship note) — cheap, immediate, and it does **not** disclose anything.

## 8. Can anything here be made patentable? Yes — but not this code

Five candidate inventions, ranked by realistic prospect. Each needs a *new* implementation with measured numbers; none is covered by what exists today.

**A. Hardware-rooted capture-to-exhibit sealing for §63 BSA (strongest).**
*Problem:* the s.63(4) hash is entered into a form *after* capture, by the same party holding the device; the SC in *Pune Bar Association* and the 2026 commentary note that hashing proves integrity of a copy but neither **attribution** nor **capture-time**, and courts hash only the original while practitioners argue the copy must be hashed too (Indian Law Live, Jun 2025).
*Invention:* seal at the sensor. On a phone/dashcam body-worn app, compute the digest over frames inside a TEE/StrongBox as the encoder writes them, sign with an attested device key bound to the OS verified-boot state, embed a C2PA-style provenance manifest that carries **the statutory Part-A and Part-B fields as first-class schema**, then Merkle-batch N exhibits into one anchor transaction and emit **per-exhibit inclusion proofs verifiable offline** (so a judge with the file + a printed proof, no network, no trust in your vendor, verifies). Add dual-hash (original + working copy) with automatic divergence report.
*Why patentable:* technical effect is concrete and measurable — bytes/second, anchor cost amortisation, offline verifiability, tamper-detection latency; it integrates with physical capture hardware; and it is not in e-Sakshya (which hashes on upload).
*Risk:* Microsoft 11,139,954 + OriginStamp/Guardtime are the neighbours; you must claim the *capture-time attestation + statutory-schema binding + offline inclusion-proof* combination, not "hash and anchor".

**B. Compiler for statutory procedure with commencement-aware execution (hardest, most defensible).**
*Problem:* this repo shows the failure mode perfectly — hardcoded "≥7 years ⇒ sections 64,65,66…" lists and a flat "60 days" that belongs to a different section, and no handling of the fact that s.176(3) applies only from a **per-State notification date within five years**. Every Indian legal-tech tool encodes the statute once and rots.
*Invention:* a pipeline that (i) parses a statute/notification version into typed obligations (`trigger`, `deadline`, `artifacts_required`, `actor`, `waiver_authority`, `commencement`, `jurisdiction`), (ii) compiles them to an executable, signed, **versioned rule artifact**, (iii) resolves at run time which rule text was in force *for that state on that date*, and (iv) emits a machine-verifiable compliance trace naming the rule version relied upon.
*Why patentable:* the technical problem is real and non-abstract (temporal rule validity, jurisdictional divergence, deterministic re-verification, avoiding silent staleness), the effect is measurable (false-compliance rate, % of obligations auto-detected vs. manual list), and the prior art (Stanford CodeX/computational law, Drools/Rete rules engines, RegRx/CompuCompliance-style financial rule automation) is mostly *outside* Indian criminal-procedure with per-notification dates.
*This is the single most valuable asset in the whole project idea.* If you file on one thing, file on this plus A.

**C. Hallucination-proofing for legal retrieval (commercially strongest, moderately patentable).**
*Invention:* claim→evidence binding where every generated assertion must resolve to a located span in a retrieved primary-source document; entailment check + citation-resolution graph (treated/covered/not-overruled via a precomputed citation graph of NJDG/SCC data); **hard refusal** where no span supports the assertion; output carries a verification manifest (doc id, page/para, digest, model+version, retrieval query) that itself is hash-anchored so a court can audit *why* the system asserted it.
*Why:* directly answers a documented, current harm (SC 2026 treating fabricated citations as misconduct), produces measurable technical effect (citation precision/recall, hallucination rate per 1k claims), and is *not* a "prompt with a schema". Your `vidhikRAG` is the anti-example.

**D. Offline-capable integrity verification for low-connectivity district courts.** Digest-and-inclusion-proof verification over one-way broadcast / QR-carried proofs; cache-efficient partial Merkle proofs sized for 2G. Small but clean technical effect (bandwidth, memory, latency) and squarely within what the IPO accepts as "improved efficiency of the underlying system".

**E. Real PQC migration for long-lived evidence.** ML-DSA/ML-KEM (via `liboqs`-style WASM), **hash-chain rolling re-signature** so exhibits anchored today are verifiably migrated before SHA-256/RSA-2048 retire, with an auditable epoch log. Genuinely useful for a 20–30-year evidence retention horizon, and *actually* the claim the README makes. Crowded with incumbent filings (Google, IBM, NQubit et al.), so a search is mandatory before writing anything.

Do **not** attempt: "a method of assessing bail/adjournment risk", "a system that drafts judgments", "a chatbot that answers legal questions". In India these are §3(k) substance (administrative/mental/abstract), they carry the *Loomis*-class due-process objection, and they collide with the judiciary's own policy posture (advisory use only, no delegation of adjudication; s.3(b) public-order grounds are available to an examiner or an opponent).

## 9. The inventorship landmine (AI assistance)

India's position as of today: the IPO **refused** the DABUS application (202017019068) on **15 April 2026**, holding an AI cannot be the "true and first inventor" under ss.6, 7, 10 — ownership of the model or the code does not confer inventorship; Thaler's appeal (C.A.(COMM.IPD-PAT) 36/2026, notice 30 Jul 2026) is **pending**, so this is not settled law. The **CRI Guidelines 2025** separately hold AI-*generated* inventions (autonomous, minimal human input) non-patentable while AI-*assisted* inventions are assessed normally, provided a human's inventive contribution is identified and demonstrated.

Why it matters here: the source tree carries strong AI-assistance fingerprints — the "to simulate quantum resistance **as requested**" comment (written to satisfy a prompt, not a specification), four parallel copies of the same feature tree, verbatim-duplicated services, `// EXIF extraction would go here`, `merkleRoot: "" // Optional implementation`, sequential invented `indiankanoon/doc/123456…` links, and a `tsc_full_output_1..20.txt` log series indicating generated code patched repeatedly without being understood.

That does not bar a patent — humans routinely use AI as a tool — but it changes what you must be able to prove. Before filing, write and date an **invention record for the human contribution**: which problem you framed, which mechanism you chose and rejected, the parameters you set, the tests you designed. The claim must rest on that, not on the generated code. A patent agent will ask precisely this, and an opponent in a s.25 pre-grant opposition can use "no human actual contribution" as a real attack.

## 11. What to fix regardless of IP

**Blocking / credibility:**
1. **Delete "quantum", "post-quantum", "CRYSTALS-Kyber" and "Zero-Knowledge" from all UI, comments, README and badges**, or implement the real thing (ML-DSA/ML-KEM; a genuine Sigma-protocol/commitment scheme). Right now these are false descriptions of `SHA256(x + salt)` and a string equality check. In a courtroom-adjacent product this is the difference between a demo and a liability.
2. **Replace the LLM-generated "quantum fingerprint" with `crypto.subtle.digest('SHA-256', buffer)`** in a Web Worker, and delete the LLM from the integrity path entirely. Hashing must never be model-generated.
3. **Remove the fabricated case corpus.** Either drop `vidhikRAG` to an honest "keyword demo over 50 hand-picked citations" or wire it to a real corpus (Indian Kanoon / SCC / NJDG) with per-document digests and verifiable locators. Sequential fake `/doc/123456/` links and a miscited *Manish Sisodia* entry are exactly the failure the Supreme Court flagged as misconduct in 2026.
4. **Fix the statutory mapping** — 60/90-day figures belong to s.187(3); s.193(3)(i) is the 90-day progress-information duty; charge-framing-in-60-days is s.263; committal 90→180 is s.232; adjournment cap (2 per party) is s.346; free FIR copy "forthwith" is s.173(2) (not "within 24 hours"); and s.176(3) only binds **from each State's notification date**. *Derive* the forensic trigger from the punishment schedule instead of a hardcoded section list.
5. **Move Gemini calls behind your own server** (or at minimum a proxy) so `VITE_API_KEY` is never in a client bundle; add a budget/rate limiter, and log an audit trail of every AI call with model+version (which you also need for any future s.63-adjacent provenance story).

**Second tier:** replace `crypto-js` with `crypto.subtle` (it's native, faster, and not a JS reimplementation of SHA-256 in your bundle); implement **real** Merkle batching + inclusion proofs (you gain the amortisation story *and* the offline-verification story); stop redacting only two name fields while shipping the whole object; add tests for `forensicInterlock` state machine (the one file with logic worth testing); strip the 20+ log files and `dist/` from git and add them to `.gitignore`.
